Visual Studio Code — це кросплатформний редактор коду, який поєднує
властивості легкого текстового редактора та інтегрованого середовища розробки.
Система підтримує редагування коду, підсвічування синтаксису, автодоповнення,
діагностику помилок, відлагодження, інтеграцію з Git, роботу з терміналом,
тестування, контейнерні середовища, WSL, SSH та GitHub Codespaces [2].
З погляду архітектури VS Code цікавий тим, що він не є монолітним
застосунком. Його функції розподілені між окремими процесами, модулями та
підсистемами. Це дозволяє редактору залишатися стабільним і розширюваним
навіть тоді, коли користувач встановлює багато сторонніх розширень або працює з
великими проєктами.
Electron використовується як базова платформа для десктопної версії.
Він поєднує Chromium для відображення інтерфейсу та Node.js для доступу
до можливостей операційної системи. Такий підхід дозволяє використовувати
вебтехнології для створення десктопного застосунку, який працює на Windows,
Linux і macOS [3].
3.2 Архітектурний стиль системи
Архітектуру VS Code доцільно розглядати як комбінацію декількох
архітектурних стилів:
–

багатопроцесна архітектура — ключові частини системи працюють в
окремих процесах операційної системи;

5
–

модульна архітектура — функції редактора розділені на незалежні
компоненти та сервіси;

–

плагінна архітектура — додаткова функціональність реалізується через
розширення;

–

протокольно-орієнтована архітектура — складні інтеграції виконуються
через стандартизовані протоколи LSP і DAP;

–

клієнт-серверна архітектура — у режимі Remote Development інтерфейс
працює локально, а середовище виконання може бути винесене на сервер,
у контейнер або WSL.

Багатопроцесний стиль є базовим для Electron-застосунків. Main Process керує
життєвим циклом застосунку, створенням вікон, меню та інтеграцією з операційною
системою. Renderer Process відповідає за інтерфейс користувача. Extension Host
запускає розширення окремо від інтерфейсу, а Language Servers та Debug Adapters
виконують спеціалізовані задачі аналізу коду і відлагодження [4].
Обґрунтування такого підходу полягає в необхідності поєднати швидкий
інтерфейс, розширюваність і стабільність. Якщо б усі компоненти працювали в
одному процесі, помилка або нескінченний цикл у розширенні міг би повністю
заблокувати редактор. Ізоляція процесів зменшує цей ризик і робить систему
стійкішою до збоїв (див. рис. Рисунок 3.1).

3.3 Основні компоненти системи
Основні компоненти VS Code наведено нижче.
Main Process — головний процес Electron-застосунку. Він відповідає за запуск
програми, створення вікон, керування меню, діалогами, оновленнями, доступом до
файлової системи та взаємодією з операційною системою.
Renderer Process — процес відображення інтерфейсу. У ньому працює
Workbench — основна частина UI редактора: панель файлів, вкладки, командна
палітра, налаштування, панель розширень, статус-бар і область редагування.
Monaco Editor — окремий компонент для відображення та редагування тексту.
Він відповідає за рендеринг коду, курсор, виділення, підсвічування, роботу з
великими файлами та інтерактивні можливості редактора [5].
Extension Host — ізольований процес, у якому виконуються розширення.
Він дозволяє стороннім розробникам додавати нові можливості до редактора, не
отримуючи прямого доступу до внутрішнього DOM інтерфейсу [4].
Language Server — окремий процес або сервіс, який відповідає за
інтелектуальні мовні функції: автодоповнення, діагностику помилок, перехід до
визначення, перейменування символів і форматування коду.

7
Debug Adapter — проміжний компонент між універсальним інтерфейсом
відлагодження VS Code та конкретним нативним дебагером, наприклад GDB, PDB
або Node.js debugger.
VS Code Server — серверна частина, яка використовується у Remote
Development. Вона запускається на віддаленій машині, у контейнері, WSL або
Codespaces і забезпечує роботу з кодом без потреби зберігати всі файли локально.
3.4 Взаємодія компонентів
Компоненти VS Code не взаємодіють через спільну пам’ять. Основним
механізмом зв’язку є передавання повідомлень між процесами. Для цього
використовується IPC (Inter-Process Communication), RPC-подібні виклики та JSONRPC [4].
Типовий потік взаємодії виглядає так:
–

користувач виконує дію в інтерфейсі, наприклад відкриває командну
палітру або запускає команду розширення;

–

Renderer Process формує подію та передає її до Extension Host через IPC;

–

Extension Host виконує код відповідного розширення;

–

якщо потрібно виконати аналіз коду, Extension Host або мовне розширення
звертається до Language Server через LSP;

–

Language Server повертає результат, наприклад список помилок або
варіанти автодоповнення;

–

результат передається назад в інтерфейс і відображається користувачу.

Такий потік взаємодії компонентів наведено на рис. Рисунок 3.2.

реалізовував підтримку кожної мови, редактор реалізує клієнт LSP, а мова реалізує

Для відлагодження використовується Debug Adapter Protocol. Його роль схожа
на патерн Adapter: VS Code має універсальний UI відлагодження, а Debug Adapter
перекладає стандартні команди DAP у команди конкретного дебагера [7].

3.5 Масштабованість та надійність
Масштабованість VS Code проявляється не тільки у здатності працювати з
великими проєктами, а й у здатності розширювати функціональність без зміни ядра
системи.
Функціональна

масштабованість

досягається

через

Extension

API.

Розширення можуть додавати підтримку мов, теми, інтеграції з інструментами,
панелі, команди, форматери, тестові адаптери та інші можливості. При цьому
розширення взаємодіють із редактором через контрольований API, а не через
прямий доступ до внутрішніх структур.
Технічна масштабованість забезпечується через LSP і DAP. Нову мову
програмування або новий дебагер можна інтегрувати через окремий сервер чи
адаптер, не змінюючи ядро редактора. Це значно спрощує підтримку великої
екосистеми.
Надійність підвищується завдяки ізоляції процесів. Помилка в одному
розширенні або мовному сервері не повинна призводити до повного падіння
редактора. Крім того, асинхронні повідомлення допомагають уникати блокування
інтерфейсу при виконанні тривалих операцій.
Remote Development демонструє масштабованість архітектури на рівні
середовища виконання. Інтерфейс може залишатися локальним, а Extension Host,
Language Servers, термінал і код можуть виконуватися віддалено (див. рис.
Рисунок 3.4) [2].

Обмеження архітектури також існують. Electron-застосунки зазвичай
споживають більше оперативної пам’яті, ніж нативні програми. Крім того, велика
кількість розширень може створювати навантаження на CPU та пам’ять. Однак
ізоляція Extension Host і лінива активація розширень частково зменшують ці ризики.

4 ВИСНОВКИ
У результаті виконання практичного заняття досліджено архітектуру
програмної системи Visual Studio Code.
Було встановлено, що VS Code поєднує багатопроцесний, модульний,
плагінний, протокольно-орієнтований і клієнт-серверний архітектурні стилі. Така
комбінація дозволяє редактору залишатися швидким, стабільним і розширюваним.
Проаналізовано основні компоненти системи: Main Process, Renderer Process,
Monaco Editor, Extension Host, Language Servers, Debug Adapters і VS Code Server.
Визначено, що взаємодія між компонентами побудована на IPC, RPC-подібних
викликах і стандартизованих протоколах JSON-RPC, LSP та DAP.
Оцінено переваги архітектурних рішень: ізоляція процесів підвищує
надійність, Extension API забезпечує масштабування функціональності, LSP і DAP
спрощують інтеграцію мов і дебагерів, а Remote Development дозволяє розділяти
інтерфейс і середовище виконання.
Отже, Visual Studio Code є прикладом сучасної складної програмної
системи, у якій правильна декомпозиція, слабка зв’язність і стандартизовані
протоколи напряму впливають на підтримуваність, масштабованість і стабільність
програмного продукту.
